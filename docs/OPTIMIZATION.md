> 参考 [HarleyCoops/Math-To-Manim](https://github.com/HarleyCoops/Math-To-Manim) 的架构，对
> Math Function Visualizer 的全面优化方案。
>
> 文档日期：2026-10-29　|　当前版本：v2.1（提交 `33cefa7`）
> 参考项目事实来源：仓库 README（32 KB）、`docs/ASTRA_PIPELINE.md`、`docs/showcase/every-orbit-great-circle/`
> 下三个阶段产物样本（`01_intent.json` / `02_knowledge_map.json` / `05_shot_list.json`）。
> **未逐行审阅其 Python 实现**，架构结论仅基于上述公开材料。

## 1. 参考项目到底做对了什么

Math-To-Manim 不是「一个画动画的脚本」，而是**一条把自然语言数学问题编译成分镜与 Manim 场景的流水线**。
截至 2026-10-28：2,810 stars、Python、MIT、仓库约 262 MB。

它的六个阶段各有专属 agent，每阶段产出一个**可校验的 JSON 契约**：

| 阶段 | 产出 | 这一阶段回答什么 |
|---|---|---|
| ① intent | `01_intent.json` | 核心命题是什么、讲给谁听、情绪曲线怎么走 |
| ② knowledge map | `02_knowledge_map.json` | 需要哪些前置概念、每个概念的「视觉种子」 |
| ③ curriculum | `03_curriculum.json` | 先讲什么后讲什么、每段的教学目标 |
| ④ math dossier | `04_math_dossier.json` | 公式、假设、参数、数值校验 |
| ⑤ shot list | `05_shot_list.json` | 每个镜头用哪个动词、作用于谁、几秒、字幕说什么 |
| ⑥ scene spec | `06_scene_spec.json` | 具体几何、材质、相机、LaTeX 位置 |

样本里的 shot 长这样：

```json
{
  "beat": 2,
  "act_number": 1,
  "verb": "ORBIT",
  "target": "orrery",
  "params": { "rate": 0.05, "run_time": 9.0 },
  "caption_text": "Five orbits around one star. Watch them come home together.",
  "seconds": 9.0
}
```

**这是整份参考里最值得抄的一条设计**：镜头用**固定动词表**（`TILT_3D` / `ORBIT` / `HEADLINE` /
`RETURN_2D` …）描述，而不是让模型直接写代码。于是分镜变成**数据**——可校验、可统计时长、可换渲染器、
可复现，出问题也能定位到「第 3 幕第 7 个镜头」而不是「代码某行崩了」。

### 1.1 七个可迁移机制

| # | 机制 | 在参考项目里的形态 | 为什么有效 |
|---|---|---|---|
| M1 | **分阶段契约** | 六份 JSON，`validate_stage_artifact` 逐份校验 | 失败发生在阶段边界，不会烂到最后一帧才发现 |
| M2 | **数学验证工具** | `execute_math_check`：沙箱 AST + NumPy 验算代数恒等式、分岔阈值、边界条件 | 「看起来对」升级为「算过是对的」 |
| M3 | **产物静态检查** | `verify_scene`：AST 语法、禁用 import、`ThreeDScene` 相机纪律 | 在渲染前拦住 80% 的低级崩溃 |
| M4 | **渲染探针** | 正式渲染前先跑一帧 still，把真实图片交给审计 | 用最小代价验证「真的能跑」 |
| M5 | **评审门与回修路由** | 评审失败按类型回到 brief / math / storyboard / scene，并作废下游审批 | 修在正确的层，不是哪儿错都改代码 |
| M6 | **运行清单与哈希** | `runs/astra/<run-id>/` + `manifest.json` + SHA-256 绑定 | 任何一帧都能追溯到输入、模型、代码版本 |
| M7 | **动词表 DSL** | `TILT_3D` / `ORBIT` / `HEADLINE` … | 生成物从「自由代码」降级为「受限数据」，可控性大幅提升 |

## 2. 两个项目的本质差异

| 维度 | Math-To-Manim | 本项目 v2.1 |
|---|---|---|
| 定位 | 把数学**讲出来**（叙事 + 3D 动画） | 把函数**算出来**（数值 + 2D 静态图） |
| 中间表示 | 六份 JSON 契约 | **无**——计算结果直接进 HTML |
| 时间维度 | 秒级分镜、镜头运动 | 只有「一次性渲染」 |
| 输出 | MP4 + 源码 + 运行清单 | PNG + CSV |
| 正确性保障 | 独立验算工具 + 评审门 | 单元测试（只覆盖算法层） |
| 可复现性 | run-id + 哈希清单 | 刷新即失，无记录 |
| 代码规模 | 262 MB / 多包 | 3.4k 行 / 5 个 JS 文件 |

**一句话差距**：本项目已经能准确回答「这个函数有什么性质」，但**没有能力把这个答案讲成一个过程**。
中间缺的不是渲染技术，而是**一层中间表示（IR）**。

## 3. 具体问题清单（带证据）

### 3.1 架构层

| 编号 | 问题 | 证据 | 后果 |
|---|---|---|---|
| A1 | 计算与呈现未解耦 | `ui.js:305-357` 的 `renderReport()` 把 13 个字段逐个拼 HTML | 报告加一项要同时改 `math-core` / `ui` / README 三处 |
| A2 | 无运行记录 | 结果只存在 `plotter.lastSamples` 内存对象里 | 刷新即失；无法回答「这张图用的什么区间、什么容差」 |
| A3 | 助手是「一跳式」 | `assistant.js:65-92` 的 `_route()` 命中即 `return` 一段字符串 | 不支持多步任务、无法自检、无法复用到动画 |
| A4 | 单表达式假设 | `ui.js:273` 只分析 `exprs[0]` | 多函数叠加时只画不析，交点之外没有对比结论 |
| A5 | 展示层承载业务 | `ui.js` 同时负责校验、调度、报告渲染、表格、CSV、聊天、FPS | 523 行 / 6 种职责，UI 层零测试 |

### 3.2 功能层

| 编号 | 问题 | 证据 | 后果 |
|---|---|---|---|
| F1 | 只有结论，没有过程 | 报告是 13 行静态文本，无「为什么」 | 学生看到 `x≈1.4142136` 但不知道是怎么得到的 |
| F2 | 无时序表达 | 图与报告同时出现，没有「先看形状→再找零点→再看极值」的顺序 | 信息密度高但认知负荷也高 |
| F3 | 无代码导出 | 只有 CSV 与 PNG | 想复现得自己写 Python；作业场景断了最后一公里 |
| F4 | 数值结论无自检 | 报告不显示零点代回残差、积分不交叉验证、极值不验一阶导 | 用户无法判断「这个近似值可不可信」 |
| F5 | 无前置知识 | 助手不会解释「什么是拐点」 | 只能当计算器，不能当老师 |
| F6 | 无参数探索 | 改参数要手动改输入框再等重绘 | 无法建立「参数→形状」的直觉 |
| F7 | 3D 能力断裂 | `ui.js` 在 3D 分支直接 `renderReportUnavailable(...)` | 三维曲面没有任何性质分析 |
| F8 | 状态不可分享 | 全仓无 `location.hash` / `pushState` | 无法把「这个函数 + 这个区间」发给人 |
| F9 | 无国际化 | `ui.js` 内 172 处中文字面量 | 无法面向英文用户 |

## 4. 迁移设计

### 4.1 五阶段流水线（六阶段的本项目版）

参考项目的六阶段里，②③④ 本质是「教学编排」，⑤⑥ 是「视觉编排」。本项目是确定性数值工具，
不需要 LLM 参与计算，因此压缩为五阶段，**②③ 由算法完成，①④ 规则化**：

```
表达式 + 区间
   │
   ├─① Intent ──────────► 01_intent.json     {expr, window, goal, audience}
   │                                         goal ∈ {property, integral, tutorial}
   │
   ├─② Plan ────────────► 02_plan.json       {tasks:[{kind, method, tol}]}
   │                                         每个 task 必须声明方法与容差
   │
   ├─③ Facts ───────────► 03_facts.json      {claims:[{id, statement, value, verification}]}
   │                                         每条 claim 必须带残差与 ok
   │
   ├─④ Storyboard ──────► 04_storyboard.json {beats:[{verb,target,params,seconds,caption}]}
   │                                         verb ∈ 白名单，总时长 15~90s
   │
   └─⑤ Present ─────────► 图 / 动画 / CSV / Python 脚本 + manifest.json
```

**每阶段一个 `validate*` 函数**，对应参考项目的 `validate_stage_artifact`：

| 阶段 | 校验规则（不通过即中止，不进入下一阶段） |
|---|---|
| ① | 表达式可 `compile`；区间 `xMin < xMax`；`goal` 在枚举内 |
| ② | 每个 task 的 `method` 在允许集合内；`tol > 0` |
| ③ | 每条 claim 有 `verification`；`residual` 为有限数；`ok` 为布尔 |
| ④ | `verb` 在白名单；`seconds > 0`；`15 ≤ Σseconds ≤ 90`；每条 beat 有 `caption` |
| ⑤ | 渲染无异常；`manifest.hashes` 覆盖全部输入与产物 |

### 4.2 分镜动词表（M7 的本项目版）

参考项目用 `TILT_3D` / `ORBIT` / `HEADLINE` 描述 3D 镜头。本项目是 2D 函数图，
对应动词表如下——**这是整套方案的核心资产**，播放器、导出器、测试都围绕它：

| verb | params | 语义 | 视觉 |
|---|---|---|---|
| `TITLE` | `text` | 标题卡 | 居中大字，淡入 |
| `PLOT` | `expr, xRange, yRange` | 画曲线 | 曲线绘制 |
| `TRACE` | `from, to` | 光点沿曲线扫过 | 动点 + 残影 |
| `MARK_ZERO` | `x` | 标零点 | 空心圆 + 竖虚线 |
| `MARK_EXTREMUM` | `x, y, kind` | 标极值 | 实心点 + 「极大/极小」 |
| `SHADE_MONOTONIC` | `from, to, dir` | 单调区间着色 | 半透明色带 + ↗/↘ |
| `MARK_INFLECTION` | `x` | 标拐点 | 菱形 + 竖直虚线 |
| `ASYMPTOTE` | `kind, value` | 渐近线 | 虚线（垂直/水平/斜） |
| `ZOOM` | `xRange, yRange` | 视窗推近 | 轴范围动画 |
| `CAPTION` | `text` | 字幕 | 底部字幕条 |
| `HOLD` | `seconds` | 停留 | — |

**为什么要动词表而不是「生成 Plotly 配置」**：配置是自由结构，无法校验、无法统计时长、
无法换渲染器；动词表可以。同一份 `04_storyboard.json`，今天用 Plotly 播，明天可以导出成
Manim 脚本或 SVG 序列，**渲染器可替换**。

### 4.3 数值自检（M2 的本项目版）

参考项目用 `execute_math_check` 验算代数恒等式。本项目对应的是**对每条结论做独立复算**：

| 断言 | 检验方式 | 通过阈值 |
|---|---|---|
| 零点 `x₀` | 代回 `\|f(x₀)\|` | `< 1e-6 · max(1, scale)` |
| 极值 `x₀` | 一阶导 `\|f'(x₀)\|` | `< 1e-4` |
| 拐点 `x₀` | 二阶导 `\|f''(x₀)\|` | `< 1e-2` |
| 定积分 `I` | `eps=1e-9` 与 `eps=1e-12` 两个解之差 | `< 1e-6 · max(1, \|I\|)` |
| 奇偶性 | `max\|f(x)∓f(-x)\|` 抽样 | `< 1e-6 · scale` |
| 周期 `T` | `max\|f(x+T)-f(x)\|` 抽样 | `< 1e-5 · scale` |
| 单调方向 | 区间内 7 点导数同号率 | `= 100%` |

**收益**：报告从「一串数字」变成「一串带残差的数字」。用户第一次能看见
「这个零点的残差是 3.2e-16」——这比任何文案都更能说明工具可信。

## 6. 不建议照搬的部分

诚实划界，避免为了「像」而付出无谓成本：

| 参考做法 | 为什么不建议 | 替代方案 |
|---|---|---|
| 双模型评审门（Astra 出稿 + Jev 打分） | 个人项目无第二模型预算；评审延迟高 | **规则化自检**（§4.3）代替主观评审 |
| 六阶段全部交给 LLM | ②③ 是确定性数值计算，LLM 只会引入不确定性 | 算法做 ②③，规则做 ①④ |
| 完整 Manim 渲染 | 需要 Python 运行时 + FFmpeg，与「纯前端、双击即用」定位冲突 | 导出 Manim/Python **脚本**，让用户自己跑 |
| 多 provider 适配（argon/mythos/sol/grok/glm/mimo） | 六套 pipeline 对个人项目是维护负担 | 只保留规则引擎，不接模型 |
| 262 MB 仓库 / 全片渲染产物 | 克隆成本高，Pages 也放不下 | 产物走 Release，不进仓库 |

### 8.2 事实层抓到的缺陷（v2.2）

`1/x` 的分析报告会给出一个**拐点 x ≈ 0**。原因是 `concavity()` 只检查二阶导是否变号，
而 `2/x³` 在 0 两侧恰好一负一正。事实层算出的残差比是 **1.8e20**，一眼看出异常。

修复：用二阶导中位数量级做门槛（`|f''| > max(1e-2, 0.01·median)` 判为极点），
并在该采样点断开凹凸区间。修后 `1/x` 返回 0 个拐点 / 2 段凹凸，`x³` 仍正确返回 1 个。

> 这个 bug 在 v2.1 之前一直存在，40 个单元测试都没抓到——因为没人想过「拐点数量」也会错。

### 8.3 静态检查抓到的缺陷（v3.0）

生成器最初把区间写成 `X_MIN, X_MAX = -10.0, 10.0`，而静态检查要求 `^X_MIN\s*=`，
两者不一致——**检查器与生成器各说各话**。这类问题如果不接「生成 → 检查 → 实跑」三段流水线，
只会在用户下载后运行失败时才暴露。

改成逐行常量后，5 个表达式全部通过检查，并用本机 Python 实跑验证了 4 个（含 `1/x` 的极点、
`exp(-x²/4)cos(3x)` 的 37 条结论）。

### 8.7 为什么搁置 i18n（O13）

界面里有 172 处中文字面量，横跨 `ui.js`、`assistant.js`、`glossary.js`、`index.html`。
只翻一半会得到「中英混排」的界面，比全中文更糟；全翻则要改动所有文案并重测每条助手回复。

判断：**当前用户是中文用户，i18n 的收益低于它的回归风险**。已在 README 路线图保留该项，
并给出替代路径——若要做，应按「先抽 `i18n.js` 字典 + `t(key)`，再按模块分批替换」的方式推进，
而不是一次性全局替换。
